## Thai details, taxonomy and private photos (v0.1.58)

The form displays Buddhist years, abbreviated Thai months, and a nullable numeric duration. Optional start/end dates use DD/MM/BE on screen; the server retains CE years and ISO dates for sorting, source IDs and history. Date precision remains an internal field; unknown/conflicting legacy dates never acquire invented days. Known contiguous legacy dates provide an initial duration, which a member may correct.

Canonical presentation channels are Online, Onsite and Other with required explanation. Legacy hybrid displays as Other / Hybrid. Reach is domestic or foreign; foreign saves require a country. Recipient organization is separate from location. Audience groups are CP, CPF, partner/customer, external organization, international seminar and Other with explanation. Both old CPF groups display as CPF; CP abroad displays as foreign / CP without inventing a country. The raw immutable import and prior revision chain are unchanged. Legacy confirmed Swine-BU scope remains intact for existing filters; changing a non-CPF record to CPF leaves its unconfirmed BU scope unknown instead of classifying it automatically.

`KnowledgeSharingDetails003.gs` projects this taxonomy on read and validates new saves. Bootstrap advertises `knowledgeSharingDetailsProtocol: 3` and `knowledgeSharingMediaProtocol: 3`. New editors send `detailsProtocol: 3`; stale older editors are rejected with a refresh message before mutation. Request IDs and optimistic revisions remain mandatory. A retry after a lost committed-save response is sent with the exact original ID before rechecking the old revision.

`KnowledgeSharingMedia003.gs` stores originals and small/report JPEG derivatives privately in the existing configured Drive folder. It never changes Drive sharing. The dedicated `KnowledgeSharingPhotos003` metadata table is created on first successful upload, not on reads. Originals accept JPG/PNG/WebP up to 20 MiB each; a record may link at most four photo IDs. Uploads are sequential so even a maximum-size original plus bounded derivatives stays below the existing 30-million-character request limit. The server checks current ownership/revision, signatures and sizes, record binding and unique upload IDs. Repeated upload IDs cannot create duplicate files or switch content. Uncommitted photos are readable only by their uploader/Admin; attached photos are readable through the normal authenticated Knowledge Sharing viewer. Drive IDs are never returned to the browser.

Removing a photo link retains originals and revision history. Failed creation cleans up only new, provably unreferenced files. A lost response after durable metadata or audit is recoverable without deleting referenced files. Gallery and original downloads use authenticated API calls. History PDF/PNG exports include report-size photo pages; multi-page PNG remains one ZIP. New server helpers use private underscore names as described in [Google's Apps Script documentation](https://developers.google.com/apps-script/guides/html/communication#private_functions), so photo operations are not exposed as callable HTML-service helpers.

## Record editing and dashboard (v0.1.57)

The authenticated `knowledgeSharing` action now supports `updateRecord`. The current deployed Code.gs bootstrap advertises `knowledgeSharingEditProtocol: 1` only when `ksEdit002` is installed. `read` returns server-computed `access.editableRecordIds`; the UI shows edit controls only for those records. The server independently reloads the ACTIVE Users role and derives ownership using `members.userId` and immutable `record.memberIds`. Any linked co-presenter may edit a shared presentation; all co-presenters see the same corrected record. Admin may edit all presentations, including former-member and team histories. Management may edit only presentations linked to their own account, just like other members. A caller-supplied role or owner ID never grants permission.

Editable fields are title, year/month/dates/precision, location, audience (blank remains unknown, 0 is known), categories, presentation channel, audience reach/group, and notes. Member identities, co-presenter ownership, source keys, original rows/fingerprints and record IDs cannot be reassigned by this endpoint. Date, category and audience fields are validated and derived flags are recalculated server-side. Each edit requires the expected record revision, reason, and stable request ID. Stale saves fail visibly. Repeating the same committed request is a no-op, while reusing its ID with a different actor or payload is rejected.

`KnowledgeSharingEdits002` is an append-only journal over the immutable imported snapshot. Each entry retains full before/after JSON, hashes, actor, timestamps, reason and revisions. STAGING rows stay invisible; an Audit entry must be durable before COMMITTED publication. Exact retries recover interrupted publication without another revision or audit. A competing request cannot overwrite pending changes to the same record. Reads validate the revision/hash chain before applying committed entries. Farms, Records, Users, costs and initial import rows are never rewritten by this editor. Initial-import replay cannot reset edited histories. No old setup or migration is required.

Dashboard graphs show annual activity, presentation channel, member credits (top 10 with the full member directory below), topic-category shares, locations (top 8 plus all remaining locations grouped), and audience groups. The same year/scope/search/member filters apply to charts, metrics and exports. Category percentages use all category assignments because one presentation may have multiple tags; member credits may overlap, while organizational totals count each presentation once. Pending source-review items remain historical evidence and are not automatically marked resolved by a general edit.

Exports offer Dashboard only or Dashboard plus **all** matching history rows, irrespective of the table's current page. PDF uses the existing raster report generator; multi-page PNG exports contain numbered PNG pages in one ZIP, avoiding multiple-download browser prompts. Both include Thai labels, selected scope, current revisions and the existing server-issued export attribution/audit. Long history text wraps and continues across pages. The export uses a stable copy of the displayed data, and controls are disabled while files are generated.

Deploy only these changes onto the verified current Backend: add `KnowledgeSharingEdits002.gs`, update `KnowledgeSharing001.gs`, add the edit capability in Code.gs bootstrap, and add `knowledgeSharing` to `prepareExport016`'s report allowlist. **Do not deploy the legacy repository Code.gs.** Workspace QA tests current captured source with in-memory Google services for ownership/forged-role denial, former/shared history, immutable source, revision conflicts, retry, interruption and corrupt journals. Browser QA covers edit/reload/no-op/conflict, six charts, filtered PDF/PNG, complete history pagination, long Thai text and mobile layout. Test artifacts distinguish local/mock from actual production verification.

## Read/import contract

The bridge calls the existing authenticated `api()` wrapper with action `knowledgeSharing`, `op: read` only if bootstrap settings advertise `knowledgeSharingProtocol: 1`. Backend must advertise that flag only after its authenticated read endpoint and authorized data are ready. The response uses the normal `{ok, data}` wrapper, where `data` has schemaVersion 2, `members`, `records`, `reviewItems`, source aliases and links. Member records require `id`, `displayName`, `kind`, nullable `userId`, `membershipStatus`, `sourceNames` and optional `sourceScope`. Presentation records require the schema fields consumed by the core/UI, including `memberIds`, source fields, year, month, dates, audience, categories, channel, reach and audienceGroup.

The Backend must enforce session and record visibility, resolve roles from server-side Users, and return only fields the viewer may access. The browser does not authorize access using a supplied member ID. A linked member uses `team.userId`, never `team.id`, to match historical data. Missing capability displays an unavailable message without sending unsupported actions or reporting zero historical activity. Unmatched IDs and read errors remain visible. Responses arriving after navigation cannot overwrite another view. Auth tokens and session data are not cached by this component.

The optional Admin initial-import page loads JSON from a local file, sends `previewImport`, and shows server-validated totals. `applyImport` requires the preview's batch ID/hash/base snapshot plus a checked confirmation. No file selection, page load or preview writes data. This page appears only for Admin when bootstrap advertises `knowledgeSharingImportProtocol: 1`; the server independently resolves current roles from Users. Read capability stays zero until a committed snapshot exists. Non-Admin imports, inactive sessions and forged client roles are rejected server-side.

## Import preparation

The importer uses dedicated `KnowledgeSharingRows001` and `KnowledgeSharingBatches001` tables. It never edits Farms, farm Records, costs, assignments, files or Users. It revalidates user ID/name pairs, source IDs, revisions, alias membership, link completeness, dates, audiences and review counts. Former people remain independent of login accounts.

The initial importer writes an immutable snapshot, preserving imported IDs/revisions, and rejects replacement of an active snapshot by a changed dataset. This deliberately prevents silent history overwrite; future editing/version upgrades require a separate reviewed operation. Apply requires the current base snapshot and confirmed server hash. Same batch/hash is a no-op; reused batch ID with changed content fails.

Publication uses STAGING -> persisted rows -> verified row hashes -> deduplicated audit -> COMMITTED receipt -> active pointer. Reads ignore staging. Recovery reuses matching staging rows and preserves their ordinals; it never overwrites conflicting staging data. An interrupted write can leave blank physical sheet rows, which do not represent business records. Receipt/hash validation prevents partial or corrupt reads. No active pointer is set until the complete batch and audit are durable. Pre-existing conflicting table headers fail before creation or overwrite.

Source duplicates, unknown dates and audience remain pending until separately confirmed. Aliases resolved by the returned workbook are retained in audit. Do not run historical migrations or infer event audience from sums/maxima.
